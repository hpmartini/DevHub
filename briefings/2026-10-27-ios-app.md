# Briefing: iOS-App für iPhone und iPad (Issue #120)

## The Job

Eine iOS-App „DevOrbit“ für iPhone und iPad, die per Xcode auf Hapes eigenen Geräten installiert werden kann. Die App ist eine Capacitor-Hülle um den bestehenden React-Build. Sie verbindet sich über das Tailscale-Tailnet mit dem DevOrbit-Server auf dem Mac und bietet v1 drei Modi, die per Touch bedienbar sind: **Agents** (`/agents`: Liste, Dispatch, Peek, Attach), **Board** (`/board`) und **Terminal** (Attach an Agent-Sessions und Shell-Tabs über `/api/pty`). Beim ersten Start koppelt Hape die App mit dem Mac: Server-Adresse plus Pairing-Token eingeben oder einen QR-Code scannen. Ab dann lehnt der Server Anfragen ohne gültigen Token ab.

## Why

DevOrbit ist Hapes Arbeitsumgebung für agentische Entwicklung „über alle Geräte hinweg“ (docs/VISION.md). Unterwegs will Hape vom iPhone/iPad aus Agents sehen, anweisen und anhängen und das Board pflegen. Die Agents sollen dabei auf dem Mac weiterlaufen. Node-Server, PTY, `claude`-CLI und code-server laufen nicht auf iOS. Deshalb ist die App ein reiner Client. Das Leitbild gilt: Mesh = Tailscale, nur unmodifizierte `claude`-CLI, keine Session-Verlagerung.

## Guardrails

- Eine Codebasis. Capacitor (`ios/`-Projekt im Repo) nutzt den Vite-Build. Mobile Anpassungen sind responsive Änderungen an bestehenden Komponenten (`components/AgentsView/`, `components/BoardView/`, `components/XTerminal`), keine Parallel-Komponenten. Das Leitbild verlangt „Eine Shell“.
- API-Basis: `utils/apiConfig.ts` erkennt heute Electron vs. Browser. Ergänze Capacitor dort, mit einer konfigurierbaren Server-URL (aus dem Pairing gespeichert). Alle `fetch`-, SSE- und WebSocket-Pfade laufen schon über `API_BASE_URL`/`getWsUrl`/`getSSEUrl`. Nachziehen, wo sie das nicht tun.
- Routing: Unter `capacitor://` ist ein HashRouter nötig wie bei Electron (`App.tsx`). Das bestehende Muster wiederverwenden.
- Server-Sicherheit (trust boundary, `server/index.js`):
  - Neuer Remote-Zugang nur, wenn er per Env/Config aktiviert ist. Default bleibt localhost-only, damit Desktop und Electron unverändert bleiben.
  - Erreichbarkeit nur übers Tailnet: `tailscale serve` (bevorzugt, bringt HTTPS/WSS) oder Bind an die Tailnet-IP, nie `0.0.0.0`.
  - Pairing-Token: zufällig, serverseitig gespeichert, per Header bzw. WS-Query geprüft, konstantzeitiger Vergleich. Gilt für REST, SSE und `/api/pty`. Localhost-Anfragen brauchen keinen Token.
  - CORS (`isAllowedOrigin`) eng um den Capacitor-Origin erweitern.
- Out of scope v1: Code-Modus/code-server, Überblick-Dashboard, Workflows, Docker-Steuerung, TestFlight/App Store, Push-Notifications, Offline-Modus.
- Annahme: `tailscale serve` steht auf dem Mac zur Verfügung (Tailscale.app ist installiert, siehe `briefings/2026-10-23-mesh-remote-agents.md`). Klappt das nicht, Fallback auf Bind an die Tailnet-IP mit HTTP. In dem Fall ATS (App Transport Security) nur für die Tailnet-Domain bzw. den 100.x-Bereich lockern.
- Annahme: Der Pairing-QR-Code wird in den Admin-/Einstellungen der Desktop-App angezeigt. Ein Kamera-Plugin ist optional, manuelle Eingabe reicht als Pflicht.
- Annahme: Signing mit Hapes kostenlosem Personal Team in Xcode. Bundle-ID `de.martinilabs.devorbit`.
- Höchstens 3 Subagents (z. B. Server-Auth, Capacitor-Setup, Mobile-Layout).

## Done means

- `bun run build && bunx cap sync ios` läuft fehlerfrei. `xcodebuild -scheme App -destination 'platform=iOS Simulator,name=iPhone 16'` baut. Dasselbe gilt für einen iPad-Simulator.
- Im Simulator, gegen den laufenden lokalen Server mit aktiviertem Remote-Zugang: Pairing klappt, die Agents-Liste lädt, ein Attach-Terminal zeigt Ausgabe und nimmt Eingaben an, das Board lädt. Screenshots von iPhone und iPad im PR.
- Unit-Tests (Vitest) für die Token-Prüfung: ohne Token → 401, falscher Token → 401, richtiger Token → 200, localhost ohne Token → 200, WS-Upgrade ohne Token abgelehnt. Außerdem für die Capacitor-Erkennung und URL-Bildung in `apiConfig`. `bun run test:run` und `bun run lint` sind grün.
- Unverändert: Desktop-Browser und Electron funktionieren ohne Konfiguration wie bisher, ohne Token-Pflicht auf localhost.
- README-Abschnitt „iOS“: Remote-Zugang aktivieren, `tailscale serve` einrichten, Pairing, App per Xcode installieren.
- Weiterarbeiten bis fertig. Stoppen und fragen nur, wenn Tailscale-Einrichtung oder Signing eine interaktive Aktion von Hape braucht.
- Rückmeldung: kurzer Bericht im PR. Was gebaut wurde, welche Annahmen getroffen wurden, was Hape auf dem echten Gerät noch prüfen muss.
